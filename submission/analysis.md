# Analysis of the original TaskSphere schema

## Evidence-based findings

The original files are `schema/broken_schema.sql` and `docs/DebugERD.png` in the [Kalvium assignment repository](https://github.com/kalviumcommunity/Project-Engineering/tree/main/Milestone-03/Debug%20a%20Broken%20ER%20Diagram). The SQL and image were both inspected. The following table distinguishes confirmed schema defects from likely effects; it does not claim that duplicate data or slow queries were measured.

| Original problem | Evidence from the original schema | Impact on the application | Proposed correction | How the correction improves the design |
|---|---|---|---|---|
| No primary keys or uniqueness rules | None of the four `CREATE TABLE` statements declares a primary key or `UNIQUE` constraint. `UserProjects` has only `user_name` and `project_name`. | Rows cannot be reliably identified, and the same user/project pair can be inserted repeatedly. Duplicate membership rows can multiply report results. This is a risk enabled by the design, not proof duplicates already exist. | Add identity primary keys to `team_members`, `projects`, and `tasks`; use `(project_id, member_id)` as the `project_members` primary key. | Rows have stable identities, and duplicate project membership is rejected by the database. |
| References are stored as names, with no foreign keys | `Projects.owner_name`, `Tasks.project_name`, `Tasks.assigned_user`, and both `UserProjects` columns are text values. The SQL declares no `FOREIGN KEY`. The ERD also connects entities without key columns. | A misspelled, renamed, or nonexistent user/project can be referenced; matching labels are not referential integrity. | Store `owner_member_id`, `project_id`, and `assigned_member_id`; declare foreign keys to the referenced primary keys. | Invalid references are rejected, and names can change without rewriting every relationship. |
| Member/project details are redundantly represented | `Users.name` and `Projects.owner_name` both hold a person's name. `Tasks.project_name`, `Tasks.assigned_user`, and `UserProjects.user_name`/`project_name` repeat entity labels. | Names can become inconsistent after edits; text joins are fragile and repeated values increase update work. | Keep member and project attributes in their own tables; represent relationships with IDs in `projects`, `tasks`, and `project_members`. | Each fact is stored in one canonical place, reducing update anomalies and supporting 3NF. |
| Project membership does not have a safe relational key | `UserProjects` stores a pair of names with no key or uniqueness constraint. The ERD shows it as the membership link. | Duplicate pairs are permitted, and names cannot reliably identify the linked rows. | Replace it with `project_members(project_id, member_id)` and a composite primary key plus two foreign keys. | The junction table represents many-to-many membership and prevents duplicate pairs. |
| No validation constraints | `Tasks.status` is an unconstrained `VARCHAR(50)`; names/emails and relationship columns have no `NOT NULL`; email has no uniqueness rule. No constraints appear elsewhere. | Missing required values and unsupported status values can enter storage; duplicate emails are possible. | Add `NOT NULL` where required, unique email, a task-status `CHECK`, and non-null junction keys. | The database rejects values outside the chosen design rules instead of relying only on application code. |
| SQL types are invalid or disagree with the ERD | The SQL uses `email ID(100)`, `user_name VAR(100)`, and `task_name INT(100)`. These are not valid built-in PostgreSQL type declarations. The ERD labels `Tasks.task_name` as a string, unlike `INT(100)` in the SQL. | The schema as written will not execute as PostgreSQL without changes; the diagram and SQL describe different types for the task name. | Use valid types such as `VARCHAR`/`TEXT` for names and email, and make the diagram match the corrected SQL. | The schema is executable PostgreSQL and the diagram is consistent with the implemented design. |
| No indexes are declared | The supplied SQL contains no `CREATE INDEX`, and absent primary/unique keys there are no indexes created for those constraints. | Joins and filters on relationship columns may become slower as tables grow. The assignment reports slow queries, but without query plans and workload data the exact cause cannot be confirmed. | Add indexes on `projects.owner_member_id`, `project_members.member_id`, `tasks.project_id`, and `tasks.assigned_member_id`. The composite membership primary key already indexes `project_id` first. | Foreign-key joins can use indexes on the referencing side; the index choices avoid duplicating the junction table's primary-key index. |

## Redesigned entities and rules

- `team_members` stores each member once. `member_id` is the primary key and `email` is unique.
- `projects` stores project details and a required owner reference. Owner deletion is restricted while owned projects exist.
- `project_members` implements the project/member many-to-many relationship. Deleting a project or member cascades to its membership rows.
- `tasks` belongs to one project and may have no assignee. A project deletion cascades to its tasks; deleting an assigned member sets that task's assignee to `NULL`.
- Task statuses are limited to `todo`, `in_progress`, `done`, and `blocked`. This allowed set is a design choice because the original status field did not define values.

## Normalization and assumptions

The design is intended to satisfy 3NF: each table represents an entity or relationship; its non-key attributes describe that table's key; and member/project names and descriptions are not repeated in task or membership records. The junction table's key is the pair of its foreign keys, with `added_at` describing that membership.

The assignment describes projects, tasks, and team members and shows ownership, membership, task containment, and task assignment. The redesign assumes each project has exactly one owner, each task belongs to exactly one project, an assignee can be any existing team member (not necessarily a project member), and a task may be unassigned. Email uniqueness and the four allowed task statuses are explicit design choices; the original files do not establish those business rules. No requirement was found to make project names globally unique or unique per owner, so neither rule is imposed.
